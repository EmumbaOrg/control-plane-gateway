Section 1

Enterprise Control Plane for AI Harnesses

What it is

A shared enterprise layer that governs, distributes, monitors, routes, and improves AI development-harness usage across the organization. Developer harnesses (e.g. Claude Code, Pi.dev, or Codex) communicate with this enterprise layer, and it mediates all LLM requests sent and received from these harnesses.

Purpose

Make AI-assisted development reliable, secure, auditable, cost-aware, consistent, and reusable across teams.

Core Design Principle

Place enforcement outside developer-controlled prompts. Implement a centralized control-plane with guidance, monitoring, analytics and policy enforcement.

Pain Points It Must Address:

  • Manual and repository-local dissemination of guidance features does not scale. Skills, agents, workflows, and policies cannot be manually maintained across hundreds or thousands of repositories.
  • Developers can bypass required processes. Prompt-based instructions and harness-level checks can often be skipped or explicitly overridden.
  • The enterprise lacks control over model access. Credentials, approved models, privacy rules, and budgets need central governance.
  • Vendor telemetry is insufficient. Harness or model provider logs do not show whether enterprise skills, workflows, agents, or quality gates were used correctly.
  • Poor inputs create poor results. Even capable models perform badly when tickets, requirements, architecture, or acceptance criteria are weak.
  • Failures/successes are not systematically reused. Repeated issues should become improved guidance, automated checks, or deterministic guardrails. Successful patterns should be incorporated into harness improvement.

Monitoring and analytics dashboard

monitoring, auditing & intelligent analytics, cost & budgets, usage and rollout. Specifically:

  • Track model calls, policy decisions, workflow stages, approvals, tool usage, and resource versions.
  • Show whether enterprise guidance was invoked—not only whether an LLM was used.
  • Detect skipped stages, unusual flows, outdated resources, and repeated overrides.

Shared resource registry

Contains Plugins, skills, subagents, prompts, workflows.

Management interface (human in the loop)

A human sits at the management layer of the control plane. A human is needed for:

  • Governance
  • Managing policies
  • Approving harness improvements before they are applied
  • Adding / removing guidance resources

Governance & Enforcement

  • Define which users and teams can access specific models, tools, MCP servers, plugins, and workflows.
  • Require approved development processes for activities such as feature implementation or pre-PR validation.
  • Apply policies through the harness-level or gateway-level controls.
  • Examples of harness-level controls: Claude Code tool permissions, approval gates, sandboxing, user roles, MCP permissions.
  • Examples of gateway level controls: enforcing model usage budgets, PII detection and privacy-sensitive model routing.

LLM Gateway and Routing

Central credentials, approved model access, intelligent routing, budgets, and private-model routing. Route requests according to capability, cost, privacy, team, repository, and data-residency policies.

Harness Improvement

Improve ticket, specification, architecture, contract, and acceptance-criteria quality before implementation

Guidance dissemination

Communicates with the shared resource repository to:

  • Centrally publish approved skills, plugins, subagents, prompts, workflows, and checks.
  • Distribute updates across teams without manually changing every repository.

Section 3

Implementation Roadmap

Select a step to expand its detail.

  1. Document the type of setup demonstrated by the client.

    Explore how Claude Code combines:

    • Plugins and repository-installed configuration
    • Skills and specialised subagents
    • Hooks, MCP tools, and project instructions
    • Project-specific architectural knowledge
    • Human approval gates and deterministic checks

    Output: Documentation of the client's current setup.

  2. Create an enterprise-managed Claude Code setup covering:

    • Identity and team configuration
    • Approved tools, models, MCP servers, and permissions
    • Sandboxing and execution policies
    • Enterprise guidance resources (e.g. skills, plugins)

    The point is to try to cover as many of Claude Control’s available enterprise controls as possible.

  3. Route supported model usage through a central gateway.

    Demonstrate:

    • Credential handling and approved endpoints
    • Privacy and data-residency controls
    • Private or local model access
    • Cheapest-capable-model routing
    • Budget, user, team, and repository constraints

  4. Create a central repository for skills, plugins, subagents, prompts, and workflows.

    Show how updates can be pushed and pulled by teams through the enterprise control plane and resource usage can be enforced at harness level without overriding local project knowledge.

  5. Instrument:

    • Skill, plugin, subagent, tool, and workflow invocation
    • Human approvals, overrides, failed checks, and skipped steps
    • Gateway decisions, model usage, cost, and policy violations

    Add enforcement through harness-level hooks and enforcement mechanisms and gateway rules.

  6. Use traces from the telemetry to identify:

    • Processes teams frequently skip or override
    • Guidance that is unclear or ineffective
    • Recurring engineering and compliance failures
    • Opportunities to replace LLM checks with deterministic validation
    • Differences in effectiveness across teams, repositories, and workflows

  7. Evaluate Codex and open-source harness integrations.

    Determine which capabilities can be:

    • Standardised across all harnesses
    • Implemented through shared protocols
    • Enforced only through external systems
    • Adapted through harness-specific connectors

    The long-term direction is to build a harness-agnostic enterprise platform.
