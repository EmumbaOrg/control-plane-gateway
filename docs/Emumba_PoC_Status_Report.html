What the PoC set out to prove

The four outcomes

  • Capture — every request and response recorded, and impossible to bypass.
  • Attribution — spend tied to a named developer, not a shared pool.
  • Budget control — a per-developer ceiling the gateway itself enforces.
  • Credential containment — the real provider key never reaches a laptop.

Verdict, in one line each

  • All four work on real traffic, with failure modes measured rather than assumed.
  • One correctness gap remains — unknown anthropic-beta headers are dropped.
  • Budgets are a brake, not a cap — the crossing request always completes.
  • The gateway now changes traffic, not only records it — see item 03.
  • Not production-ready — see the security items in Section 11.

The sentence that explains the whole design

Anthropic only ever sees the real key, developers only ever hold a virtual key, and spend is recorded against the virtual key — so we get attribution and enforcement without ever distributing the real credential.

Revoking a developer is one database row. No key rotation, no redeployment across laptops.

LiteLLM Proxy Server plus PostgreSQL, run with Docker Compose. Claude Code is simply told a different address — nothing is patched, reverse-engineered, or MITM'd. Client configuration is two environment variables.

Why
Without a per-person ceiling, one developer can spend the whole team's allocation, and there is no way to cap exposure before an invoice arrives.
How
LiteLLM stores max_budget and budget_duration in the credential's own PostgreSQL row. On every request the auth layer reads that row and compares accrued spend against the ceiling — a local database read, no network call, no real key needed. That is exactly why it can run before the key swap.
Budgets can sit at four levels, and a request is checked against all of them — the most restrictive wins:
Organization  →  Team  →  Internal User  →  Virtual Key
Proof
A key capped at max_budget: 0.002, then real traffic pushed through it. Six calls succeeded; the seventh onward were refused with 429. Documented both ways — the dashboard route and a scripted six-step curl walkthrough — in limited_budget_per_dev.md. Total cost of one full verification run: $0.000225.
Findings
  • Recommendation: put the cap on the Internal User, not the key — it then follows the person across every credential they hold. Mint keys with max_budget blank.
  • Refused calls cost nothing. 13 refused requests logged 0 tokens and $0 — stopped at the gateway, never sent to the provider. This is the property worth demonstrating.
  • It is a brake, not a hard cap. The crossing request always completes, because price is only known after the call. Measured overruns: 12% on a realistic budget, 29× on a deliberately tiny one.
  • Sizing matters more than expected. One message reading "reply with just hi" cost $0.18 — Claude Code ships its system prompt and every tool definition on the first message, so ~47k input tokens is the floor for any turn. Start developers at $20–50 / month.
  • Reset Budget: Not set is a lifetime cap. Without budget_duration the budget never refills and the key dies permanently. Always set monthly.
Open risk — this will be reported as an outage. Over-budget returns 429 from the auth layer, which blocks every route including /v1/models. Claude Code cannot tell it apart from a rate limit and burns all ten retries against a budget that will not reset for weeks. Needs a support runbook before rollout.
Not yet tested: throttling instead of hard-blocking (budget_exceeded_throttle_percentage), and Budget Fallbacks (Opus → Sonnet → Haiku on a per-model breach).
Why
Being able to say "this developer may use Haiku but not Opus" is how model cost and data exposure get governed centrally, rather than by asking people nicely.
How
A models allowlist on the virtual key, and/or Personal Models on the Internal User. Enforcement sits in the same auth layer as the budget, so the request is refused before the provider is called. Changes apply in place via POST /key/update — the key string, max_budget and accrued spend are untouched, so nothing has to be re-issued to the developer.
Proof
A key scoped to claude-haiku-4-5-20251001 was asked for claude-opus-5. The refusal came back in LiteLLM's own wording, not Anthropic's — see the message quoted under Figure 2. That wording is the proof the gateway refused it itself, before any token was billed.
Findings
  • Restricting a key to a single model breaks Claude Code mid-session. It needs a Haiku-class model for background traffic (titles, summaries) as well as the model you picked. Scope to a set, never to one.
  • no-default-models blocks at the user level, not the key. A user created through the UI can carry that sentinel, meaning "no models except through a team" — every call is then refused with a 403 no matter what the key allows. Fix: Personal Models = all-proxy-models, or put them in a team.
  • GET /v1/models returns the calling key's allowlist, not the gateway's config. Add a model to config.yaml without updating the key and clients keep seeing the old list — which looks exactly like the config change having failed. Re-run /key/update after every model change.
Why
The highest-value control-plane capability of the five. It moves enforcement from credentials and cost onto content — injecting standards, redacting secrets before they leave the network, and applying policy to what is actually sent.
How
LiteLLM's CustomLogger exposes async_pre_call_hook(user_api_key_dict, cache, data, call_type); returning a dict replaces the body that gets forwarded. Our custom_capture.py already subclassed CustomLogger and was already registered — so this was one method on an object the proxy was already loading. No new wiring.
The risk that had to be cleared first: whether the hook fires on /v1/messages at all. That route behaves differently from the others — it is the reason the anthropic-beta gap exists — so it was plausible the hook was skipped there. It is not. Read from the installed source: anthropic_endpoints/endpoints.py:101 dispatches through base_process_llm_request(route_type="anthropic_messages"), and common_request_processing.py:1518 awaits pre_call_hook and assigns the result back. Unaffected by the anthropic-beta gap, which concerns outbound headers, not the body.
Shipped
Two behaviours, both individually switchable, both fail-open.
  • (a) max_tokens clamp — on by default, ceiling 8000. Claude Code reserves 32000 output tokens on every request and providers gate on the reservation, so a 60-token reply gets refused. The CLI can be fixed with an environment variable; the desktop app cannot, so server-side is the only place that fixes every client at once.
  • (b) Secret redaction — off by default. High-specificity credential patterns in outbound message content are replaced before the request leaves our network. Off by default deliberately: it rewrites developer content, so enabling it should be a decision with a named owner.

Findings
  • The exempt list matches exactly, never by prefix — this is load-bearing. claude-haiku-4-5-gmn-37-flash is a picker alias for Gemini and starts with claude-haiku-4-5. Prefix matching would silently exempt every translated route and defeat the clamp on exactly the models that need it.
  • Redaction touches messages only — never system or tools. Those are the cacheable prefix, so rewriting them risks the caching win for no benefit. tool_result blocks are walked, and they are the point: they carry the file contents and command output where a committed credential actually surfaces.
  • Replacements are deterministic — no counters or timestamps in the placeholder. Claude Code resends the whole conversation every turn, so a varying placeholder would change the cached prefix and cause a silent ~10× input-cost increase.
  • Audit trail: every modification appends one line to capture/modifications.jsonl recording the kind of secret and the count, attributed to a named key — never the value. Logging the value would defeat the purpose.
  • This also closed the outstanding desktop-app 402 recorded as "Still unsolved on desktop" in NON-ANTHROPIC-MODELS.md. One hook covered both items.
Fail-open, deliberately — and the honest consequence. The hook runs in front of every request, so both behaviours fall through to the unmodified body on any error. A modification we failed to apply is a gap; a gateway that refuses all traffic is an outage. That trade is the right way round for a PoC, but it means redaction is best-effort, not a guarantee. It must not be described as a control that cannot fail, and it is not a substitute for developers not pasting credentials in the first place.
Not built: injecting Emumba standards into the system prompt — the third option considered. Same hook, but it touches the cacheable prefix, so block ordering needs care. Full detail in litellm-gateway/GATEWAY-MODIFY.md.
Why
It tests whether the gateway is a genuine control point or just an Anthropic passthrough — and whether cheaper models can be offered under the same budgets, attribution and capture.
How
No code was written. LiteLLM already exposes an Anthropic-format /v1/messages endpoint that translates to any provider it supports, and Claude Code already talks to whatever ANTHROPIC_BASE_URL points at. The whole change was model_list entries in config.yaml plus one environment variable. Provider: OpenRouter — one key reaches Google, DeepSeek, MiniMax and NVIDIA — with Groq entries alongside, and z.ai reached first-party (Section 6).
The round trip, in one line. Claude Code sends its usual Anthropic body to the gateway → LiteLLM resolves the alias, runs auth, budget, clamp and capture on the Anthropic body, then rewrites it into OpenAI format → OpenRouter routes it to the vendor's native API → the OpenAI-format stream comes back and LiteLLM re-assembles it as a valid Anthropic SSE sequence, tool calls included. Step by step, with the field-level mapping, in Figure 1, row C.
Proof
A real claude CLI session ran against a free NVIDIA Nemotron route, was asked to read a file with its Read tool, and returned the file's contents. Claude Code → gateway → OpenRouter → NVIDIA → back, with a tool round-trip in the middle.
Findings
  • 36 model routes registered — 4 Anthropic, 16 honest provider aliases, 16 Claude-shaped picker aliases. (Count as of 4 Sep 2026. Includes two first-party z.ai routes and their picker aliases — see Section 6.)
  • Tool calling survives translation — the thing most likely to break. The streamed response is a correct Anthropic SSE sequence: content_block_start with a tool_use block, input_json_delta, stop_reason: "tool_use".
  • Costing is exact to the last digit. LiteLLM billed $0.000263625; OpenRouter's own API independently reported $0.000263625 — so budget enforcement on these routes is trustworthy.
  • Capture, attribution and budgets behave identically regardless of which provider served the request. This is the argument for doing this at the gateway rather than with per-developer tooling like claude-code-router, which has no central budget or audit trail.
  • Headline gotcha: Claude Code reserves 32000 output tokens on every request and providers gate on the reservation, not on what is produced — so free and low-balance accounts reject the traffic with a 402 that reads as a broken model. CLAUDE_CODE_MAX_OUTPUT_TOKENS=8000 fixes it; claude-gw.sh sets it by default.
  • Desktop app needed a shim. The app's model picker hard-vetoes any model ID naming a vendor — the rule was read out of the app bundle. Fixed with vendor-free Claude-shaped aliases plus picker-shim (nginx on 4001) rewriting the display labels. Port 4000 and the CLI are unchanged.
Costs must be pinned by hand, or budgets silently stop working. None of these provider IDs are in LiteLLM's built-in cost map, and an unpriced model bills at $0 — spend never accrues and max_budget never trips. It fails open, and fails quietly, which for a budget-enforcement PoC is worse than the model not working at all. Each paid entry now carries explicit model_info prices; re-check whenever a model is added.
Two accepted losses, and one standing risk. Prompt caching is gone on these routes (cache_read_input_tokens: 0 — but see Section 6, where the direct z.ai route does cache), and drop_params: true had to be scoped to them — so some Claude Code features degrade silently rather than erroring. Anthropic traffic is untouched. Separately: Anthropic states they do not support routing Claude Code to non-Claude models through any gateway. Every breaking release is ours to absorb — record it as a risk, not a solved problem.

① The path. Delivery, file access and model capability are three separate problems. Judge distribution from capture/modifications.jsonl and the gateway log — never from the model's silence, and never from the model's own account of which skill it used.
Refreshing the catalogue and upgrading an install are two separate commands — claude plugin marketplace update litellm then claude plugin update emumba-react@litellm. Running only the first upgrades nothing. To check whether a skill was loaded rather than merely offered, check_skill_usage.py reads Claude Code's own per-skill usage counter:

This counter measures the marketplace path only, and it is not sufficient evidence. It is blind to gateway injection by construction — an injected skill never passes through the Skill tool, so the number correctly stays at zero while the standard is in fact applied. How it works
One SKILL.md reaches the model by two independent paths, and the distinction is the whole finding of this item.
  • ① The marketplace path — distribution. The gateway serves metadata; Claude Code clones from GitHub directly, not through the gateway, and writes the plugin to ~/.claude/plugins/cache/litellm/<plugin>/<version>/. The CLI then offers the skill to the model, which may or may not choose to load it.
  • ② The injection path — activation. The pre-call hook in custom_capture.py appends matching skill bodies straight into the request's system field, so the standard applies on models that could not call the Skill tool even if they wanted to. Which skills, and what makes each relevant, is a manifest — skills-inject.json — so adding a skill is a data change, not a code change. Two plugins are now wired this way: emumba-react (1 skill) and emumba-backend (3 skills — REST conventions, Spring Boot, Node/Express), four injectable skills in total. Each carries its own trigger regular expression; adding the fourth required no change to custom_capture.py, which is the claim this item was meant to test.
Three details that make path ② safe rather than merely clever. It is appended, never inserted: Claude Code puts its cache_control breakpoint on the last system block it sends, so text added after it sits outside the cached prefix and prompt caching is untouched — inserting earlier would invalidate the cache every turn, the ~10× input-cost failure the fidelity checks exist to catch. The default mode is installed, not always: the hook detects opt-in by matching the skill's own catalogue line inside the <system-reminder> Claude Code already sends, so it aids people who installed the plugin instead of rewriting the prompts of people who did not — always is available, and is a deliberate decision with a named owner. Triggers are matched with that catalogue removed: it lists every skill by description, and a description trips its own trigger, so the two checks deliberately read different text — triggers see the conversation without the catalogue, the installed-check sees it with. Both halves of that split were found the hard way; see Findings. And it is auditable: every injection records the skill, the byte count and the mode to capture/modifications.jsonl, because an audit trail that cannot tell "helped someone who opted in" from "modified someone who did not" is not much of an audit trail.
Both paths read the same file. The container mounts each plugin's own skills directory read-only rather than holding a copy, so the marketplace and the injector cannot drift into teaching different things.
../plugins/emumba-react/skills:/app/skills/emumba-react:ro
../plugins/emumba-backend/skills:/app/skills/emumba-backend:ro
One mount per plugin, not one shared mount. A single flat :/app/skills can only ever serve one plugin: the second such line shadows the first, and the skills it replaced stop injecting silently — no error, and indistinguishable from a trigger that simply did not match. Nesting also makes the manifest path mirror the skill's namespaced name (/app/skills/emumba-backend/rest-api-conventions/SKILL.md for emumba-backend:rest-api-conventions), so a wrong path is visible on sight.
Findings
  • Layout is not negotiable. Claude Code discovers skills only at <plugin-root>/skills/<name>/SKILL.md. A repo nesting them by category installs cleanly and loads zero skills — so third-party catalogues must be mirrored into a flat layout, not registered directly.
  • Include a .claude-plugin/plugin.json, or skills get namespaced by the version directory instead of the plugin name.
  • Use the url git-source form. The github form makes Claude Code clone over SSH, which fails on any machine without a github.com host key.
  • Governance limits, verified against the schema: no team_id and no key scoping — every enabled plugin is visible to everyone, so no per-team catalogues. marketplace.json needs no authentication. Disabling removes discovery only; existing installs keep working. No install telemetry anywhere.
  • The skill catalogue triggers every skill — found 15 Sep 2026, and latent until the fourth skill. Claude Code advertises the installed catalogue inside a <system-reminder>, one line per skill including its description — and a description trips its own trigger (spring-boot-service: Spring Boot service structure … matches the Spring Boot pattern). With the catalogue in scope, every installed skill injected on every request regardless of topic: measured on a pure Express file, it pulled in React and Spring Boot alongside the two that belonged — 17,683 characters of mostly irrelevant standard. The bug was invisible while one skill was configured, because a lone skill re-triggering off its own catalogue entry is indistinguishable from working; it only surfaced at four. Fixed by stripping <system-reminder> blocks before trigger matching, while the installed-check keeps the full text. A capability that behaves correctly in a one-item demo and incorrectly in production is the failure mode this PoC exists to find.
  • Injection silently skipped the developer who had just opted in — found 15 Sep 2026. A plugin installed in the current session is advertised by name only until its SKILL.md metadata is indexed — the "Restart to apply changes" window. The installed-check required a trailing colon after the name, so those installs read as not-installed and injection was skipped for exactly the person who had just opted in. It failed silently, looking identical to a trigger that did not match. The colon is now optional. Both bugs failed quiet rather than loud, which is why neither was caught by use.
  • The version field in the LiteLLM catalog is decorative — found 31 Aug 2026. The gateway advertised 0.2.0 while every install sat on 0.1.0, and claude plugin update reported "already at the latest version (0.1.0)". The version the CLI honours comes from the cloned repo's .claude-plugin/plugin.json, not the catalog entry. So bumping the version in the LiteLLM dashboard does not ship an update — an admin would believe they had released while nobody received it, with no error anywhere. Developers must run both marketplace update and plugin update; refreshing the catalog alone does not upgrade an installed plugin.
Distribution is deterministic; activation is not. Given a React file with a deliberate performance bug and asked for a review without naming the skill, claude-sonnet-5 auto-loaded the skill and claude-haiku-4-5 did not. Publishing a skill does not guarantee any session uses it, and cheaper models may ignore the curated catalogue entirely — so skills are advisory guidance, not a control. This matters for any compliance framing.
Open item — now doubled. Each plugin's registered marketplace source is a separate external repository, not this one — so plugins/emumba-react/ and plugins/emumba-backend/ here are the review copies and the injection source, not what developers receive over the marketplace path. The "one file, both paths" guarantee therefore holds only within this host: the gateway injects from the local directory, while a developer installs from the external repo, and nothing enforces that the two agree. Reconcile them before offering this to anyone — and note that with two plugins the reconciliation is now two repositories, each of which must live on its default branch, since the source schema has no branch or ref field.

How an Anthropic-format request reaches a non-Anthropic model, and comes back

This is the mechanism behind action item 04, and the question a demo audience asks first: Claude Code only speaks the Anthropic Messages API, and NVIDIA, Google, DeepSeek, MiniMax and z.ai do not. Nothing in Claude Code is patched and no translation code was written. The translation is LiteLLM's own /v1/messages endpoint — an Anthropic-shaped front door that adapts in both directions — and OpenRouter is the single upstream that fans one API key out to four of those vendors. z.ai is reached first-party instead, with its own key — the translation described here is identical either way (Section 6).

The round trip, step by step

  • 1 · Claude Code sends what it always sends. It has no idea a non-Claude model is involved. It POSTs an ordinary Anthropic body — model, system, messages with typed content blocks, tools with input_schema, max_tokens, stream: true — to ANTHROPIC_BASE_URL, which points at the gateway on :4000 instead of api.anthropic.com. That redirection is the only change on the client.
  • 2 · The gateway resolves the alias, not the vendor. model: "nemotron-free" is matched against model_list in config.yaml and resolves to openrouter/nvidia/nemotron-3.5-lightning:free. The openrouter/ prefix is what selects the provider adapter; the developer's virtual key never leaves the gateway and the OpenRouter key is injected here.
  • 3 · Control-plane work happens before any translation. Virtual-key auth, budget check, the output-token clamp from item 03, and capture all run on the Anthropic-format body — so what is audited is what Claude Code actually said, not a translated approximation.
  • 4 · Anthropic → OpenAI on the way out. LiteLLM rewrites the body into the OpenAI Chat Completions shape OpenRouter expects (mapping below) and drops the Anthropic-only params OpenRouter would reject outright — this is the drop_params: true scoped to these routes.
  • 5 · OpenRouter is a router, not a model. It takes an OpenAI-format request, picks a healthy upstream for nvidia/nemotron-3.5-lightning:free, and speaks each vendor's native API on the far side. One key, one billing account, four vendors — which is why it was chosen over four direct integrations.
  • 6 · OpenAI → Anthropic on the way back. The provider streams OpenAI-format chunks; LiteLLM re-assembles them into a valid Anthropic SSE sequence — message_start, content_block_start, content_block_delta, message_delta, message_stop — and normalises usage. Claude Code parses it as if Anthropic had answered.
  • 7 · The tool loop closes. When the model calls a tool, the reverse mapping produces a tool_use block and stop_reason: "tool_use"; Claude Code runs the tool locally and sends a tool_result block back, which step 4 turns into an OpenAI role: "tool" message. This is the leg most likely to break, and it is the one that was verified end to end with a real claude session reading a file.
  • 8 · Spend is priced on the way out. Token counts come back in OpenAI form, are converted, and are multiplied by the hand-pinned model_info prices — the step that fails silently at $0 if a price is missing.

The diagram for all of this is Figure 1, row C — it sits with the architecture figure rather than here, because row B's "OpenRouter / Groq" branch is exactly what row C expands: the same request path, drawn at field level in both directions, with the two measured losses marked on it.

Why this is the interesting result. The gateway is not an Anthropic passthrough — it is a real control point that can re-shape traffic and still enforce policy. Per-developer routers such as claude-code-router achieve the same model switch with no central budget, no audit trail and no attribution. The counterweight stands unchanged: Anthropic states it does not support routing Claude Code to non-Claude models through any gateway, so every breaking release is ours to absorb.

How the non-Anthropic models reach the desktop app's model picker

Getting the models to work was configuration. Getting them to appear in the Claude Code desktop app was the harder half, and it is the part most likely to be asked about in a demo, because the CLI and the app behave differently. What follows is what the app actually does — read out of its own bundle — and the two-part fix now running.

The symptom, and why it is not a misconfiguration

The LiteLLM dashboard listed every model. The desktop picker showed only the four claude-* ones. Two independent causes, neither of them ours:

  • The desktop app ignores ANTHROPIC_BASE_URL and settings.json. It reads gateway routing only from its own third-party inference configuration, so nothing exported for the CLI reaches it.
  • Model discovery filters by name. The gateway advertises every route on GET /v1/models — verified — and the app drops any ID that does not look Anthropic before rendering the picker. LiteLLM's dashboard applies no such filter, which is the entire discrepancy.

The actual filter rule, read out of app.asar

This was first inferred from what survived, and the inference was wrong in the way that mattered. The rule is client-side, in the app bundle's [custom-3p] discovery function — search for anthropic_family_tier. Reduced to readable form: 

// deny list is a HARD VETO, evaluated FIRST — a claude- prefix cannot rescue an id
DENY  = /deepseek|gemini|gemma|glm|gpt|grok|kimi|llama|minimax|mistral|
         nemotron|openai|qwen|codex|\bds-|dpsk|… ~50 vendor tokens …/
ALLOW = ['claude','sonnet','opus','haiku','fable','mythos','anthropic']

isClaudeName(id) = DENY.test(id) ? false
                                 : BARE.test(id) || ALLOW.some(w => id.includes(w))

keep(m) = isClaudeName(m.id) || TIERS.includes(m.anthropic_family_tier)

Two things follow, and both were confirmed the expensive way. Setting inferenceModels explicitly does not work — contrary to the vendor documentation, the same name check is applied to an explicit list, and the app reports each rejection in its configuration warnings. And the check runs a second time when the picker list is assembled, so anthropic_family_tier — which passes discovery — still never puts a row in the picker. Its real job is deciding what the bare sonnet / opus / haiku aliases resolve to, so injecting it would silently steal those from the real Anthropic models. Renaming is not one option among several; on a gateway provider it is the only one.

The fix, in two parts

Part 1 — the ID has to survive the deny list. Each provider model got a second, Claude-shaped alias carrying a tier plus a vendor-free abbreviation, every one checked against the regex individually before being committed: gmn avoids gemini, dsk avoids both \bds- and dpsk, zai avoids glm, nvda avoids nemotron, mmx avoids minimax. Part 2 — the label. Those IDs are unreadable, and the picker labels each row display_name || id.   • Spend logs confirm the alias routed to the right upstream: one turn selected on claude-haiku-4-5-nvda-free was served by openrouter/nvidia/nemotron-3.5-lightning:free.

Selecting a free model does not make the session free, and does not keep prompts off Anthropic. Measured, not assumed: on a turn served entirely by Nemotron, spend logs still showed two anthropic/claude-haiku-4-5 rows. Where the translation is lossy

Anthropic-specific features with no OpenAI equivalent have nowhere to go and are dropped. This is a real limit of the approach, not a bug in the setup, and it applies to every non-Anthropic route — the native anthropic/ routes skip translation entirely and are unaffected.

  • Prompt caching. cache_control has no upstream concept, so cache_read_input_tokens is always 0. Prompt caching does not exist on this route.
  • Extended thinking budgets and anthropic-beta headers.
  • output_config and other Anthropic-only parameters — which is why drop_params: true is set per model on these entries and never applied to Anthropic traffic.
The translation working correctly looked like a bug. The first probe returned HTTP 200 and empty text: content:[{"type":"thinking",…},{"type":"text","text":""}] with stop_reason:"max_tokens". Nothing had failed. qwen3 is a hybrid reasoning model, so it emitted message.thinking; LiteLLM faithfully carried that to reasoning_content and then to an Anthropic thinking block — which consumed the entire 64-token budget before the answer started. Re-measured on 3 Sep 2026, prompt “Reply with exactly: OK” at a 64-token budget: with think:false — 2 output tokens, "OK", done_reason: stop; without it — 64 output tokens entirely inside a 272-character thinking field, content empty, done_reason: length. That token-and-stop-reason outcome is the deterministic part and is the actual defect. Wall-clock figures quoted elsewhere in the repo for this comparison (9.3s versus 0.4s, and 4.0s in config.yaml) are not reproducible as a pair — the same think:false call measured 3.69s cold and 0.10s warm, so those numbers reflect KV-cache state rather than the setting. The status code is 200 the whole way up, so nothing in the stack reports the failure. gateway-up.sh now smoke-tests for exactly this signature and names the missing config key.

Measured performance, and why the first turn is slow

The dashboard logged a 214-second request, which needed explaining before this route could be recommended. It is not the gateway and not the translation: that call was 19,501 input tokens for 20 output tokens, and prompt prefill on this hardware runs at roughly 100 tokens per second. 19,501 ÷ 97 ≈ 201s — about 94% of the wall clock was the model reading Claude Code's preamble, not writing an answer.

19,501 tokens is the figure after the gateway had already made the single biggest cut. The modification audit for that exact call records tools_slimmed 36 tool definitions down to 3, saving ~14,525 tokens, alongside a max_tokens clamp from 32,000 to 8,000. Unslimmed, the request would have been roughly 34,000 tokens against a 32,768-token ceiling — it would not have fit at all, and the route would have failed rather than merely been slow. Two consequences worth stating plainly: the “shorter preamble” lever below is already partly pulled, so the remaining headroom is smaller than the raw number suggests; and this route is only usable at all because a server-side hook removes capability from it.

Why the decision was moved into the gateway

The alternative is a written instruction: "when you work on this client, switch the picker to the local model." That is a control which fails the first time someone is in a hurry, and it fails silently — nobody finds out until the prompt is already at a third-party provider. Moving the decision to the gateway makes it the default rather than an act of discipline, and it applies to the CLI and the desktop app at once, because both are just HTTP clients of the same control point.

Be equally clear about what this is not. It is a keyword match on request text, not data classification. It catches a conversation that names the client; it does not catch one that pastes the client's config without ever naming them. The keyword is matched deliberately widely to shrink that gap, which buys coverage at the price of false positives — but no keyword rule closes it. It is a strong default and a useful audit signal; it is not a data-loss-prevention boundary, and it should not be described to a client or an auditor as one.

The flow, in plain steps

  1. The developer sends a message. Claude Code posts Anthropic Messages format to the gateway with whatever model the picker has selected — say claude-haiku-4-5. Nothing on the client side knows this section exists.
  2. The gateway does its normal control-plane work first — virtual-key check, model ACL, budget gate — then hands the request body to the pre-call hook in custom_capture.py.
  3. The hook builds the text it will search. The system prompt plus the message history, concatenated newest message first, up to GATEWAY_ROUTE_SCAN_CHARS (2,000,000 characters by default). Newest first because that is where the signal is: the file just opened, the question just asked.
  4. It runs the rule list in order and the first match wins. The shipped rule looks for one keyword, extreme network, as a case-insensitive substring with an optional separator and no word boundaries — so singular, plural, hyphenated, run together and buried inside a longer word all trigger.
  5. On a match, the model on the request is rewritten to local-qwen3-8b. If the rule's target is already the selected model, it is a no-op and deliberately not logged — a developer who chose the local route should not generate override lines in the audit trail.
  6. The rest of the hook then runs against the new model, and this ordering is load-bearing: the max_tokens clamp (32,000 → 8,000) and the tool slimmer (36 tool definitions → 4, roughly 14,500 tokens saved) both key off the model name. Without them the request does not fit the local model's 32,768-token context, and Ollama truncates the overflow in silence rather than erroring.
  7. LiteLLM's router resolves the rewritten name to ollama_chat/qwen3:8b and posts to Ollama on the host. The prompt never leaves the laptop. The response is converted back to Anthropic content blocks and the client renders it normally.
  8. Three records are written, all naming the model that actually answered rather than the one the picker asked for — see the table below. This is the part that keeps cost attribution and analytics honest: without it, local traffic would be booked against Haiku.

Adding a model to the gateway — a walkthrough

Written for someone who has never touched this stack. It covers the two models added most recently — a private local model (Ollama) and a hosted vendor (z.ai) — and what Claude Code does with them once configured. Configuration and API calls only: no code is written to add a model.

The one idea to hold on to

Claude Code speaks one API — Anthropic's /v1/messages — and sends it to whatever address ANTHROPIC_BASE_URL names. Point that at the gateway, and the gateway can answer with any model it likes, because LiteLLM exposes an Anthropic-shaped /v1/messages endpoint of its own and translates in both directions. Nothing in Claude Code is patched. Adding a model is a config edit.

The files you will touch

FileWhat it holdsNeeded for
config.yamlThe model_list — one entry per route the gateway offersEvery model. This is the main file
docker-compose.ymlCredentials and addresses, passed into the container as environment variablesAny model needing a key or a host address
picker-shim/nginx.confDisplay-name rewrites for the desktop app's model pickerOnly if the model must appear in the desktop app

Anatomy of a model_list entry

Every route has the same shape, local or hosted. model_name is the name callers ask for. litellm_params.model is <provider>/<model id> — the provider prefix is what tells LiteLLM which API to speak and which host to reach. 

model_list:
  - model_name: the-name-callers-use      # what goes in "model": "…"
    litellm_params:
      model: provider/model-id            # selects the provider integration
      api_key: os.environ/SOME_KEY         # read from container env, never written inline
      drop_params: true                    # drop Anthropic-only fields the provider would reject
    model_info:
      input_cost_per_token: 0.0000001      # see the warning below
      output_cost_per_token: 0.0000001
      max_input_tokens: 200000             # what GET /v1/models advertises
      max_output_tokens: 128000
⚠ A model with no price is exempt from budgets. LiteLLM logs "Skipping all budget checks for zero-cost model", so a route priced at 0 never accrues spend and max_budget never trips on it. It fails open, and it fails quietly. That is why the free routes here carry a small invented per-token cost rather than zero — a stand-in so attribution and enforcement keep working. Those figures are not money owed.

Walkthrough A — the private local model (Ollama)

No API key and no provider account. The model runs on the developer's own machine.

Step 1
Run Ollama on the host with two environment variables that matter: 
# OLLAMA_HOST=0.0.0.0 — Ollama binds 127.0.0.1 by default, which Docker's host
#   gateway CANNOT reach; the container gets connection refused without this.
# OLLAMA_KV_CACHE_TYPE=q8_0 — quantises the KV cache so a 32k window fits in RAM.
OLLAMA_HOST=0.0.0.0 OLLAMA_KV_CACHE_TYPE=q8_0 ollama serve
Step 2
Pass the address into the container. In docker-compose.yml, under the litellm service's environment: block: 
OLLAMA_API_BASE: ${OLLAMA_API_BASE:-http://host.docker.internal:11434}
host.docker.internal, not localhost — inside the container, localhost is the container.
Step 3
Add the route to config.yaml. This is the whole change: 
  - model_name: local-qwen3-8b
    litellm_params:
      model: ollama_chat/qwen3:8b     # ollama_chat, NOT ollama — see below
      api_base: os.environ/OLLAMA_API_BASE
      drop_params: true
      num_ctx: 32768                # Ollama defaults to 4096 and truncates SILENTLY past it
      think: false                  # qwen3 emits a reasoning block before any visible text
    model_info:
      input_cost_per_token: 0.0000001
      output_cost_per_token: 0.0000001
      max_input_tokens: 32768       # keep in step with num_ctx
      max_output_tokens: 8192

ollama_chat/, not ollama/

Two different providers in LiteLLM. The plain one uses Ollama's legacy completion route, which has no tool-call support — and Claude Code cannot run without tool calling. The chat provider is mandatory here, not a preference.

num_ctx is load-bearing

Ollama defaults to a 4096-token context and silently truncates anything longer — no error, just a model that has not seen most of its own system prompt. Claude Code's system prompt alone is far past 4096.

think: false

qwen3 emits its whole reasoning block before any visible text, so time-to-first-visible-token is prefill plus the entire reasoning pass. Without this the client can give up before the first byte arrives.

Walkthrough B — a hosted vendor (z.ai)

Same shape as the local model, plus the one thing it did not need: a credential. This is the pattern to copy for any hosted vendor.

Step 1
Get an account key, and check what it can actually reach. z.ai's Flash tier is a $0 line item on their own price list — free, not expiring trial credit — so an account is needed but a card is not. Anything above that tier needs account balance. Check this before writing config, or the route will be registered and then fail on first use: 
# heredoc, not python -c: an indented continuation line inside -c is an IndentationError
docker exec -i litellm-gateway-litellm-1 python - <<'PY'
import litellm, os
r = litellm.completion(model='zai/glm-4.7-flash',
                       api_key=os.environ['ZAI_API_KEY'],
                       messages=[{'role': 'user', 'content': 'Reply with exactly: OK'}],
                       max_tokens=512, drop_params=True)
print(r.choices[0].message.content)
PY
A model the account cannot afford answers Insufficient balance or no resource package. Please recharge. rather than anything that looks like a configuration error.
Step 2
Ask LiteLLM what it already knows about the vendor's models — prices, context limits, and tool-call support all come from its built-in cost map. This decides which model id to pick and whether you must pin prices by hand: 
docker exec -i litellm-gateway-litellm-1 python - <<'PY'
import litellm
for k, v in sorted(litellm.model_cost.items()):
    if k.startswith('zai/'):
        print(k, v.get('input_cost_per_token'), v.get('max_input_tokens'),
              v.get('max_output_tokens'), v.get('supports_function_calling'))
PY
#   zai/glm-4.5-flash  0  128000  32000  True
#   zai/glm-4.7-flash  0  200000 128000  True
Two things must be true of whatever you pick: tool calling is supported (Claude Code cannot run without it), and the output ceiling clears what the client asks for.
Step 3
Pass the key into the container. In docker-compose.yml, under the litellm service's environment: block — the same place OLLAMA_API_BASE went: 
ZAI_API_KEY: ${ZAI_API_KEY:-}
The :- default makes the variable optional, so anyone running the stack without a z.ai account is unaffected by its absence. The key lives in the server's environment. It is never written into config.yaml, and it never reaches a laptop.
Step 4
Add the route to config.yaml. Note what is absent: no api_base, because LiteLLM's native zai provider already resolves to https://api.z.ai/api/paas/v4. 
  - model_name: zai-glm47-flash
    litellm_params:
      model: zai/glm-4.7-flash    # the prefix picks the provider AND the host
      api_key: os.environ/ZAI_API_KEY
      drop_params: true
      thinking:                     # GLM is a reasoning model — see the card below
        type: disabled
    model_info:
      input_cost_per_token: 0.0000001    # nominal, NOT zero — see the card below
      output_cost_per_token: 0.0000001
      max_input_tokens: 200000
      max_output_tokens: 128000
Step 5
Confirm the model string resolves where you expect, rather than assuming it. This prints the provider LiteLLM selected and the host it will call: 
docker exec litellm-gateway-litellm-1 python -c \
  "import litellm; p = litellm.get_llm_provider('zai/glm-4.7-flash'); print(p[1], p[3])"
#   zai https://api.z.ai/api/paas/v4
Step 6
A second model from the same vendor costs one more entry and no new credential — the key is already in the environment. This is the whole of the second z.ai route: 
  - model_name: zai-glm45-flash
    litellm_params:
      model: zai/glm-4.5-flash
      api_key: os.environ/ZAI_API_KEY
      drop_params: true
      thinking:
        type: disabled
    model_info:
      input_cost_per_token: 0.0000001
      output_cost_per_token: 0.0000001
      max_input_tokens: 128000      # a SMALLER window than the 4.7 route above
      max_output_tokens: 32000
Because the two windows differ, the launcher needs a per-model context arm — see the client-variables table below.

The prefix is the integration

zai/ selects a native LiteLLM provider, which is why no api_base appears in the entry — the host is built in. A vendor without a native provider needs an explicit api_base, the way the Ollama route does. Check with get_llm_provider before assuming either way.

thinking: disabled, and its limit

GLM emits a reasoning block before any visible text, so a small output budget returns empty content. This flag reduces reasoning but does not remove it — roughly 256 output tokens is still the floor. reasoning_effort is not the knob here: it is accepted and silently does nothing.

Free, but priced anyway

The Flash tiers cost nothing — GLM-4.7-Flash and GLM-4.5-Flash are listed as Free on z.ai's own pricing page — but a route priced at 0 is exempt from max_budget entirely and logs $0 spend. The nominal per-token figures exist so budgets and attribution keep working on the routes that would otherwise escape them. They are invented, not billed.

⚠ The free tier is roughly 1 request/second, and it bites. Reproduced on this stack: zai-glm47-flash returned "Rate limit reached for requests" while zai-glm45-flash answered normally in the same window. The two routes are throttled independently, so the second is genuine spare capacity — but nothing routes to it automatically. LiteLLM says as much in the error: Available Model Group Fallbacks=None. Registering two routes does not, on its own, make a rate-limited vendor resilient.

Optional — making it appear in the desktop app

The CLI accepts any model_name. The desktop app does not: its picker hard-vetoes any model ID that names a vendor, so a route called glm-… or qwen… never appears. Two things are needed.

  • A second, Claude-shaped alias in config.yaml — the same litellm_params under a vendor-free name. The two examples here are claude-sonnet-4-5-zai-47f and claude-sonnet-4-5-local-q3-8b. The abbreviation must not spell the vendor: both glm and llama are on the deny list, which is why zai-47f and local-q3-8b are used. Get this wrong and the alias silently never appears, with no error anywhere.
  • One line in picker-shim/nginx.conf, because LiteLLM sets display_name to the ID and offers no hook to override it. The shim — nginx on port 4001 — rewrites it on the way out: 
    sub_filter '"display_name":"claude-sonnet-4-5-zai-47f"' '"display_name":"GLM-4.7 Flash direct, free (gateway)"';

Applying the change, and proving it worked

Restart
config.yaml is read at boot, so the container must be restarted: 
docker compose restart litellm
Is it up?
curl http://localhost:4000/health/liveliness
#   "I'm alive!"
Is the route advertised?
Every registered model_name appears here. This endpoint is also what the desktop app reads to build its picker: 
curl -s http://localhost:4000/v1/models \
  -H "Authorization: Bearer $VKEY"
Does it answer?
This is the same Anthropic-format request Claude Code sends. Nothing in it is provider-specific — only the "model" value changes between a local model, z.ai, or Anthropic itself: 
curl -s http://localhost:4000/v1/messages \
  -H "x-api-key: $VKEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{"model":"zai-glm47-flash","max_tokens":512,
       "messages":[{"role":"user","content":"Reply with exactly: OK"}]}'
A working route returns "stop_reason": "end_turn" with the text in content[]. A model name that is not registered returns 400.

Giving a developer access

Developers never receive the provider key. They get a virtual key minted by the gateway, scoped to named models and carrying its own budget. Adding a model to config.yaml does not by itself grant anyone access to it — the models array on the key decides that. 

# Authenticated with the MASTER key, which stays on the server.
curl -s -X POST http://localhost:4000/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"models":["zai-glm47-flash"],"max_budget":5,
       "metadata":{"developer":"firstname.lastname"}}'

A request for a model not on the key is refused with 403. Over budget is 429. Both are decided before the provider is called, so nothing is billed.

Pointing Claude Code at it

Two environment variables. Nothing is patched or reverse-engineered. 

export ANTHROPIC_BASE_URL="http://localhost:4000"
export ANTHROPIC_AUTH_TOKEN="sk-…the virtual key…"
unset ANTHROPIC_API_KEY

claude --model zai-glm47-flash
⚠ That unset is not optional. If a real Anthropic key is still in the environment, Claude Code sends it as x-api-key, and that wins over ANTHROPIC_AUTH_TOKEN. The gateway then rejects a perfectly valid Anthropic key for not being a virtual key — which looks nothing like the actual cause. claude-gw.sh exists partly to make this impossible: it launches through env -u ANTHROPIC_API_KEY.

For the desktop app, a GUI application never sees shell exports. The same two values go in ~/.claude/settings.json under an env block, and the app must be fully quit and reopened: 

{
  "env": {
    "ANTHROPIC_BASE_URL": "http://localhost:4000",
    "ANTHROPIC_AUTH_TOKEN": "sk-…the virtual key…"
  }
}

Two client variables that are not optional on these routes

VariableSet toWhy
CLAUDE_CODE_MAX_OUTPUT_TOKENS 8000 Claude Code reserves 32,000 output tokens on every request, and providers gate on the reservation rather than on what is produced. Free and low-balance accounts reject the traffic with a 402 that reads as a broken model.
CLAUDE_CODE_MAX_CONTEXT_TOKENS per model Claude Code does not recognise these aliases, so it assumes a default window and must be told the real one: 32000 for the local model, 190000 for glm-4.7-flash, 120000 for glm-4.5-flash.

claude-gw.sh sets both automatically per model, which is why it is the recommended way to launch. Its per-model context selector is a shell case, and the narrower pattern must come first — case takes the first match, so a single *zai-* arm would hand the 128k model the 200k figure.

What one request actually does, once configured

  • 1 · Claude Code sends an Anthropic-format POST /v1/messages to localhost:4000, carrying the virtual key.
  • 2 · The gateway checks, in order: is the key valid (401 if not), is this model allowed for this key (403), is the key within budget (429). A failed check stops the request before the provider is called, so nothing is billed.
  • 3 · It swaps the virtual key for the real provider credential held in its own environment — or for no credential at all, on the local route.
  • 4 · It translates the Anthropic body into the shape that provider expects, and drops the Anthropic-only fields (drop_params: true).
  • 5 · The provider answers, and the response is translated back into Anthropic format — content blocks, tool_use, stop_reason, usage counts — so Claude Code parses it as though Anthropic had replied.
  • 6 · The capture callback writes the request, the response, and a spend record attributed to the named key. This step is identical on every route, which is the whole point: capture, attribution and budgets do not care which vendor served the request.
The short version: one model_list entry, one environment variable if the provider needs a key, one docker compose restart litellm, and one curl to prove it. Everything else — capture, budgets, attribution, the model ACL — is inherited.

Section 11

Security items requiring a decision

Each of these is acceptable while everything is bound to localhost. Each of them blocks a shared deployment. They need the control owner, not an engineer.

Blocking — must be resolved before any shared use

  • The master key is hand-chosen, and it is the only thing separating an operator from every captured prompt. Re-verified 22 Sep 2026: the earlier form of this item — a placeholder key published as an example in the repository's own README — no longer applies. config.yaml reads os.environ/LITELLM_MASTER_KEY, and no literal key appears in any README or tracked file. What remains is the decision, not the leak: the operative key is whatever a human typed into .env, it is not generated, and the dashboard signs in with it. It mints keys, revokes them, and reads every captured prompt. Replace with a generated secret before handing keys out, because rotating it invalidates existing virtual keys.
  • The LiteLLM image is pinned to a moving main-latest tag. Still true — re-checked 22 Sep 2026. LiteLLM shipped credential-stealing malware in PyPI releases 1.82.7 and 1.82.8. Pin a digest before this gateway handles anything real.
  • Capture retention and access are undefined. The files contain client source code, command output and developer machine fingerprints. Who may read them, where they live, and for how long are open questions.
  • Prompt rewriting has quietly become a multi-plugin surface, and its policy has no reviewer. Skill injection now spans two plugins and four skills, each governed by a trigger regular expression in skills-inject.json — a plain data file with no approval step, no owner and no test. A trigger decides whose prompts get rewritten, so it is a policy statement, and the 15 Sep catalogue bug proved the failure is not hypothetical: a mis-scoped match injected every skill into every request and reported nothing. This needs the same named owner the redaction pattern list needs. It is the same class of risk as the GATEWAY_ROUTE_RULES keywords, which are already treated as a permission list.

Hygiene — quick fixes, worth doing now

  • PostgreSQL port 5432 is mapped to the host for PoC convenience. Remove the mapping.
  • Two files hold a live virtual key in plaintext (.vkey and vkey.json). Both are correctly git-ignored by the root .gitignore and neither has ever been tracked — verified with git check-ignore — so there is no exposure today. Worth knowing they exist, and that the credential sits on disk unencrypted.
  • Auth tokens would cross the network in plaintext the moment this leaves localhost. TLS in front is not optional.
  • Secret redaction is built but switched off. Turning it on needs a named owner for the pattern list — SECRET_PATTERNS is a literal in custom_capture.py, so adding a pattern is still a code change, and a wrong pattern corrupts prompts silently.
  • Developers are not told when their prompt was modified. The audit line goes to the gateway, not the session — someone whose credential was redacted sees only that the model behaved oddly. With four injectable skills this now affects more sessions than when the item was written.
  • Plugins are installed from external repositories the gateway does not control — and there are now two. Claude Code clones from the registered git source directly, not through the gateway, and marketplace.json requires no authentication. So the "one file, both paths" guarantee holds only on this host: the gateway injects from plugins/ here, while a developer receives whatever is on the external repo's default branch. Nothing detects divergence. Reconciling this is listed as an open item in Section 3; it belongs here too, because it is a supply-chain path into developer machines.
  • The gateway now instructs the model what to say about its own provenance. Injected skill blocks tell the model to name the skill when asked, added because weaker models receive injected text as ordinary system prompt and deny using any skill. It is a reasonable fix for a real measurement problem, but it means a model's self-report is no longer independent evidence that guidance was applied. Any compliance framing must rely on an output A/B, not on asking.
  • Closed 22 Sep 2026: the broken FINDINGS-BUDGETS.md reference in limited_budget_per_dev.md — verified fixed, no remaining reference.
Per Emumba's ISO 27001 posture, none of the above should be described as a control that is "in place". Everything in this report is a PoC finding pending verification with the relevant control owner — the capture store in particular would need a documented retention and access decision before it holds real client work.
