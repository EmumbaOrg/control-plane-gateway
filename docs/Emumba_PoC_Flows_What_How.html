01

The gateway, and why traffic cannot go around it

Figure 1Claude Code without the gateway, with it, and with a non-Anthropic model

What

A gateway we operate, sitting between Emumba developers' Claude Code and the model provider. Without it, traffic goes straight to Anthropic: nothing is recorded, spend is a single shared pool, and every laptop holds a real provider key.

With it, four properties hold at once — capture (every request and response recorded, and impossible to bypass), attribution (spend tied to a named developer), budget control (a per-developer ceiling the gateway enforces itself), and credential containment (the real provider key never reaches a laptop).

Row C is the same picture with a non-Anthropic model behind it: the client is unchanged and the provider never sees an Anthropic body, so budgets, capture and attribution are identical on every route.

How

LiteLLM Proxy Server plus PostgreSQL, run with Docker Compose. Claude Code is simply told a different address — nothing is patched, reverse-engineered or MITM'd at the TLS layer.

  • Client configuration is two environment variables — ANTHROPIC_BASE_URL and ANTHROPIC_AUTH_TOKEN. No certificates, no modified binary.
  • Services: litellm (the proxy, port 4000), postgres (keys, budgets, spend), picker-shim (nginx on 4001, desktop-app labels).
  • Code written for the PoC: custom_capture.py (capture + modification hooks), run_checks.py (16-point fidelity harness), stub_upstream.py (zero-cost fake provider), capture-tap/tap.py, claude-gw.sh (validating launcher).
  • Why it cannot be bypassed: traffic must traverse the gateway to work at all — verified by stopping the proxy, at which point Claude Code fails outright.
  • drop_params: false is set globally on purpose, so LiteLLM never silently discards request fields it does not recognise.

Budgets and model access — three gates before the provider

Figure 2The three enforcement gates — each one verified live

What

Every request passes three checks before a provider is ever called: is the virtual key valid (401), is this model allowed for this key (403), and is the key within budget (429).

Because all three are decided locally, a refused call costs nothing — 13 refused requests logged 0 tokens and $0. The refusal wording is LiteLLM's own, which is the proof the gateway inspected and refused the request itself rather than relaying an Anthropic error.

How

  • Budget: max_budget and budget_duration live in the credential's own PostgreSQL row; the auth layer compares accrued spend against the ceiling on every request — a local database read, no network call. Budgets can sit at four levels (Organization → Team → Internal User → Virtual Key) and the most restrictive wins.
  • Model list: a models allowlist on the virtual key and/or Personal Models on the Internal User. Changes apply in place via POST /key/update — key string, budget and accrued spend untouched.
  • Put the cap on the Internal User, not the key, so it follows the person across every credential they hold; always set budget_duration: monthly, or the budget never refills and the key dies permanently.
  • Scope to a set of models, never one — Claude Code needs a Haiku-class model for background traffic as well as the one the developer picked.

Two behaviours to plan around. The budget is a brake, not a hard cap — the crossing request always completes, because price is only known after the call (measured overshoot: 12% on a realistic budget, 29× on a deliberately tiny one). And over-budget returns 429 from the auth layer, which blocks every route including /v1/models; Claude Code cannot tell it apart from a rate limit, so it needs a support runbook before rollout.

03

Credential containment — the real key never leaves the server

Figure 3The credential swap — the trust boundary is the design

What

Anthropic only ever sees the real key, developers only ever hold a virtual key, and spend is recorded against the virtual key — so we get attribution and enforcement without ever distributing the real credential.

Revoking a developer is one database row. No key rotation, no redeployment across laptops. A leaked virtual key is worthless off our network.

How

  • The real ANTHROPIC_API_KEY lives only on the gateway host, in the container's environment. It is substituted into the outbound request after all three gates have passed.
  • Virtual keys are minted per developer with POST /key/generate, carrying their own models allowlist, max_budget and a metadata.developer tag for attribution.
  • Four credentials exist, in descending blast radius: the provider key (gateway host only), LITELLM_MASTER_KEY (administrator — mints keys and can read every captured prompt), the per-developer virtual keys, and the PostgreSQL user (internal only).
  • unset ANTHROPIC_API_KEY is not optional on the client — a real key still in the environment is sent as x-api-key and wins over ANTHROPIC_AUTH_TOKEN. claude-gw.sh launches through env -u ANTHROPIC_API_KEY to make that mistake impossible.
04

Modifying the request in flight — clamp and redaction

Figure 8Where request modification happens — the pre-call hook

What

The gateway changes traffic, not only records it. This is the highest-value control-plane capability of the five: it moves enforcement from credentials and cost onto content.

Two behaviours ship, both individually switchable and both fail-open:

  • A max_tokens clamp, on by default, ceiling 8,000. Claude Code reserves 32,000 output tokens on every request and providers gate on the reservation, so a 60-token reply gets refused with a 402. The CLI can be fixed with an environment variable; the desktop app cannot — so server-side is the only place that fixes every client at once.
  • Secret redaction, off by default. High-specificity credential patterns in outbound message content are replaced before the request leaves our network.

How

  • LiteLLM's CustomLogger exposes async_pre_call_hook(user_api_key_dict, cache, data, call_type); returning a dict replaces the body that gets forwarded. custom_capture.py already subclassed CustomLogger and was already registered — this was one method on an object the proxy was already loading. No new wiring.
  • The hook does fire on /v1/messages — read from the installed source: anthropic_endpoints/endpoints.py:101 dispatches through base_process_llm_request(route_type="anthropic_messages"), and common_request_processing.py:1518 awaits pre_call_hook and assigns the result back.
  • The exempt list matches exactly, never by prefix — claude-haiku-4-5-gmn-37-flash is a picker alias for Gemini and starts with claude-haiku-4-5, so prefix matching would silently exempt every translated route.
  • Redaction touches messages only, never system or tools — those are the cacheable prefix. tool_result blocks are walked; that is where a committed credential actually surfaces. Replacements are deterministic, so the cached prefix does not change between turns.
  • Audit trail: every modification appends one line to capture/modifications.jsonl recording the kind of secret and the count, attributed to a named key — never the value.

Fail-open, deliberately. The hook runs in front of every request, so both behaviours fall through to the unmodified body on any error. A modification we failed to apply is a gap; a gateway that refuses all traffic is an outage. That trade is right for a PoC, but it means redaction is best-effort, not a guarantee, and must not be described as a control that cannot fail.

Skill distribution — two paths from one file

Figure 14How a skill reaches the model — two paths from one file

What

Central distribution of vetted engineering guidance — every developer gets the same reviewed material without anyone copying files by hand across hundreds of repositories. Two plugins are wired today: emumba-react (1 skill) and emumba-backend (3 — REST conventions, Spring Boot, Node/Express), four injectable skills in total.

One SKILL.md reaches the model by two independent paths, and that distinction is the whole finding: the marketplace path is distribution, and the injection path is activation.

How

  • Path ① — the marketplace. LiteLLM's UI "Skills" page is really a Claude Code plugin registry: it stores git-source metadata, serves it at GET /claude-code/marketplace.json (no authentication), and developers add it with claude plugin marketplace add. Claude Code then clones the repository itself, directly from GitHub — not through the gateway. The CLI offers the skill to the model, which may or may not choose to load it.
  • Path ② — injection. The pre-call hook appends matching skill bodies straight into the request's system field, so the standard applies even on models that could not call the Skill tool. Which skills, and what makes each relevant, is a data file — skills-inject.json, one trigger regular expression per skill. Adding the fourth skill needed no code change, which is the claim this item set out to test.
  • It is appended, never inserted — Claude Code puts its cache_control breakpoint on the last system block, so text added after it sits outside the cached prefix and prompt caching is untouched. Default mode is installed (detected from Claude Code's own <system-reminder>), not always, so it aids people who opted in rather than rewriting the prompts of people who did not.
  • Triggers are matched with that catalogue removed — the two checks deliberately read different text. The catalogue lists every skill by description, and a description trips its own trigger, so trigger matching sees the conversation without it while the installed-check sees it intact. See the red note below for why.
  • Both paths read the same file — the container mounts each plugin's own skills directory read-only rather than holding a copy, so the marketplace and the injector cannot drift. One mount per plugin, not one shared mount: a single flat :/app/skills can only serve one plugin — the second such line shadows the first, and the skills it replaced stop injecting silently.
  • Layout is not negotiable: Claude Code discovers skills only at <plugin-root>/skills/<name>/SKILL.md, and the plugin needs a .claude-plugin/plugin.json. Use the url git-source form; the github form clones over SSH and fails on any machine without a github.com host key.

Two bugs the second plugin exposed — 15 Sep 2026. Both failed silently. ① The catalogue triggered every skill. Claude Code advertises installed skills inside a <system-reminder>, one line each including the description — and a description trips its own trigger (spring-boot-service: Spring Boot service structure … matches the Spring Boot pattern). So every installed skill injected into every request regardless of topic: measured on a pure Express file, it pulled in React and Spring Boot alongside the two that belonged — 17,683 characters of mostly irrelevant standard. The defect was invisible at one skill, because a lone skill re-triggering off its own catalogue entry is indistinguishable from working; it surfaced only at four. ② Injection skipped the developer who had just opted in. A plugin installed mid-session is listed by name only until its metadata is indexed, and the installed-check required a trailing colon — so the freshest opt-in read as not-installed. Both are fixed. The lesson is the one that generalises: a capability that behaves correctly in a one-item demo is not evidence it scales.

Three limits worth stating plainly. The version field in the LiteLLM catalogue is decorative — the version the CLI honours comes from the cloned repo, so bumping it in the dashboard does not ship an update, with no error anywhere. There is no team_id and no key scoping, so no per-team catalogues and no install telemetry. And activation is the model's choice: given the same file and no explicit instruction, Sonnet auto-loaded the skill and Haiku did not — skills are advisory guidance, not a control, which matters for any compliance framing.

And it cannot be measured by asking. The skillUsage counter is blind to injection by construction — an injected skill never passes through the Skill tool, so it correctly reads zero while the standard is in fact applied. Self-reports are worse: a SKILL_USED= line is unreliable in both directions, since weaker models receive injected guidance as ordinary system text and deny using a skill, and will equally claim one they never loaded. Only an output A/B holds — same request with injection on and off, compare whether the answer cites the skill's specific rules. Injected blocks now also prompt the model to name the skill, which makes that self-report self-fulfilling for the injection path: useful in a demo, but not independent evidence.

A private local model, driven from unmodified Claude Code

Figure 10One local request, end to end — every hop, format and conversion

What

Claude Code driven by a model running entirely on the developer's own laptop — no provider account, no API key, and no prompt leaving the machine — while spend attribution, budget enforcement, prompt capture and the request-modification hooks all continue to work.

That is the result worth reporting: a fully offline model the provider never sees and cannot bill still appears in the spend log, still counts against a developer's budget, and still has its full prompt captured. Three wire formats appear in sequence (Anthropic → OpenAI → Ollama) and Ollama never sees Anthropic format at any point.

How

  • Three pieces, none of which touch Claude Code's code: Ollama on the host, one model_list entry in config.yaml, and a Claude-shaped alias so the model appears in the desktop picker.
  • OLLAMA_HOST=0.0.0.0 — Ollama binds 127.0.0.1 by default, which Docker's host gateway cannot reach. Single most likely cause of a "local model is broken" report.
  • ollama_chat/qwen3:8b, not ollama/ — the plain prefix uses the legacy /api/generate route, which has no tool-call support, and Claude Code cannot run without it.
  • num_ctx: 32768 — Ollama defaults to 4096 and silently truncates; think: false — qwen3 emits its whole reasoning block before any visible text and consumes the entire output budget otherwise.
  • A nominal, deliberately non-zero per-token cost (1e-7). LiteLLM skips all budget checks for a zero-cost model, so a genuinely free route would be exempt from max_budget entirely — disabling the very enforcement the PoC exists to prove.
  • Host memory is the real constraint: run Ollama with OLLAMA_KV_CACHE_TYPE=q8_0, or a 32k window spills to CPU and looks like a hang rather than an error.

Checking the service is running

Run from litellm-gateway/. Every command below was executed on the PoC host on 15 Sep 2026; the comments are its real output.

# the whole chain in one command — Docker, Ollama, its environment, the model,
# the stack, both ports, container → host reach, and the virtual key
./gateway-up.sh --status

# is the service up at all?
pgrep -fl ollama                   # 8641 ollama serve
curl -s http://localhost:11434/    # Ollama is running
ollama list                        # on disk:  qwen3:8b  5.2 GB
ollama ps                          # resident in RAM right now — empty when idle

# is it bound where the container can reach it?
# (cause #1 of a "the local model is broken" report)
lsof -nP -iTCP:11434 -sTCP:LISTEN  # TCP *:11434 — NOT 127.0.0.1:11434
ps eww "$(pgrep -f 'ollama serve')" | tr ' ' '\n' | grep '^OLLAMA'
#   OLLAMA_HOST=0.0.0.0        OLLAMA_KV_CACHE_TYPE=q8_0
#   OLLAMA_FLASH_ATTENTION=1   OLLAMA_KEEP_ALIVE=30m

# the same question asked from inside the container — the image has no curl
docker compose exec -T litellm python -c \
  "import urllib.request; print(urllib.request.urlopen(
   'http://host.docker.internal:11434/', timeout=5).read().decode())"
#   Ollama is running

Reading its logs

# Ollama writes to stdout and keeps no log file of its own — there is no
# ~/.ollama/logs/ on this host. gateway-up.sh redirects it, so this is the log:
tail -f ollama-serve.log

# one line per model call, with the wall clock — this is where the slow cold
# first turn and the fast warm turns are visible
grep '/api/chat' ollama-serve.log | tail -5
#   [GIN] 2026/09/14 - 14:45:56 | 200 | 3m37s | 127.0.0.1 | POST "/api/chat"

# if that file is missing or stale — where is stdout actually going?
lsof -p "$(pgrep -f 'ollama serve')" | awk '$4 ~ /^1w/ {print $NF}'

# the gateway's side of the same request
docker compose logs -f litellm

Honest framing for a demo: "first turn about three minutes, every turn after about five seconds." A measured 214-second first call was 19,501 input tokens for 20 output tokens — about 94% of the wall clock was the model reading Claude Code's preamble at ~100 tok/s, not writing an answer. Ollama's KV prefix cache then reuses that preamble, so the cost is paid once per session, not per turn. Viability here is a hardware question, not an integration one.

z.ai — a first-party provider, added without code

Figure 11One z.ai request, end to end — every hop, format and conversion

What

A whole new provider added as a configuration change, not an engineering one. z.ai is reached first-party through LiteLLM's native zai provider, with an Emumba-held key: one account, one hop, one party seeing the prompt. Zero lines of code.

Every control-plane property — key check, model ACL, budget gate, capture callback — applies to the new routes unchanged, because they all run before the vendor is ever chosen. That is the strongest available evidence that this is a genuinely provider-neutral control point rather than an Anthropic passthrough with extras bolted on.

And prompt caching survives the translation: an identical 23,810-token prefix sent three times was billed in full once and served from cache on both repeats.

How

  • Two model_list entries and one environment variable. Translation happens exactly twice, in one place, and nothing about it is z.ai-specific — which is why the same machinery absorbed the next provider too.
  • Routes registered: zai-glm47-flash (200k in / 128k out, the default) and zai-glm45-flash. Both support tool calling, which is non-negotiable.
  • Free here means free, not expiring trial credit — but only the exact ids glm-4.7-flash and glm-4.5-flash. Plain GLM-4.7 and GLM-4.7-FlashX are both paid, one character away.
  • The effective control on a reasoning model is the output budget, not the flag. thinking: {type: disabled} reduces reasoning, it does not remove it: at max_tokens: 64 zero runs produced text, at 256 all five did. Do not smoke-test this route at 64 tokens and conclude it is broken. Related trap — reasoning_effort is accepted and silently does nothing.
  • Alias naming is load-bearing: glm is on the desktop picker's deny list, hence zai-47f and zai-45f.

The free tier is roughly 1 request/second and it bites — and no fallback is configured between the two routes (Available Model Group Fallbacks=None). A developer pinned to the 4.7 route gets a hard rate-limit error and has to switch by hand. Adding fallbacks in config.yaml is a prerequisite before this is offered to more than one person at a time.

OpenAI — the same path, re-tested, and where it stops

Figure 12One OpenAI request — every hop, and the exact point it stops today

What

The provider-neutrality claim, re-tested on a second vendor — and it held. One model_list entry, one environment variable, no code. The gateway resolved the route, authenticated against OpenAI, and reached the provider on the first attempt.

This is also the section to be most careful about: the route has never returned a completion. OpenAI accepted the credentials and then refused on billing — the account balance is zero, not merely low. Everything up to the provider boundary is verified; the last hop is not, and a 429 cannot rule out a second problem behind it.

How

  • gpt-4.1-nano was chosen over the cheaper gpt-5-nano on failure modes, not on price — the saving is about $0.0015 per thousand calls. gpt-5-nano is a reasoning model that rejects max_tokens, rejects a non-default temperature, and bills invisible reasoning tokens; each is a 400 indistinguishable at a glance from a bad key — precisely the ambiguity a connectivity test exists to remove.
  • Pricing is cross-verified — LiteLLM's built-in cost map and OpenAI's published page agree to the digit, so unlike the OpenRouter entries this route needs no hand-pinned model_info and does not fall into the silent-$0 budget failure.
  • A billing failure is a diagnostic: 401, 404 and 429 divide the failure space cleanly into our key, our config and their balance. verify_openai.py prints which of the three it is.
  • Verified today: route registered (pass), cost map populated (pass), POST /v1/chat/completions and POST /v1/messages — both 429 insufficient_quota.

Decision needed: fund the account, or comment the entry out. Leaving it registered, failing and unexplained is the one option that is not defensible — and it breaks the rule the z.ai section set for itself, that a route answering every call with a billing error reads as a broken gateway.

Content-based route override — keeping a client's work on-prem

Figure 13The route-override decision — where it happens, and what it writes down

What

Keeping one client's work on-prem, by default rather than by discipline. The gateway reads the text of each request and, when the conversation names a client whose work is scoped to on-premise inference, serves that request from the private local model — whatever model the developer picked. The developer changes nothing.

One rule ships enabled: a conversation mentioning Extreme Network — any spelling, singular or plural, even buried inside a longer word — is answered by local-qwen3-8b. The alternative was a written instruction to switch the picker by hand, which is a control that fails the first time someone is in a hurry, and fails silently.

Be equally clear about what this is not. It is a keyword match on request text, not data classification. It catches a conversation that names the client; it does not catch one that pastes the client's config without naming them. It is a strong default and a useful audit signal — it is not a data-loss-prevention boundary, and should not be described to a client or an auditor as one.

How

  • The hook builds the text it will search — system prompt plus message history, concatenated newest first, up to GATEWAY_ROUTE_SCAN_CHARS (2,000,000 characters). Newest first because that is where the signal is.
  • Rules run in order, first match wins, and on a match the model on the request is rewritten. If the developer had already selected the target model it is a no-op and deliberately not logged.
  • Ordering is load-bearing: the rest of the hook then runs against the new model, so the max_tokens clamp and the tool slimmer (36 tool definitions → 4, ~14,500 tokens saved) both key off the rewritten name. Without them the request does not fit the local model's 32,768-token context, and Ollama truncates the overflow in silence.
  • Three records are written, all naming the model that actually answered rather than the one the picker asked for — which is what keeps cost attribution honest.
  • Matching is deliberately wide — no word boundaries, [\s\-_]* between the words — so a branch name like extremenetworksmigration fires. The accepted cost is over-matching ("extreme network latency" routes local), asserted in the test suite rather than merely tolerated: a false positive costs one developer one degraded answer and is visible; a false negative sends client material to a hosted provider and nobody sees it at all.
  • Rules are deployment configuration, not code — one JSON object in GATEWAY_ROUTE_RULES adds a client. Treat it like a permission list: without word boundaries, a short keyword is dangerous in a way it was not before.
  • Verified: 24/24 offline logic checks, plus 12 real overrides in the live audit trail showing model: ollama_chat/qwen3:8b against client_model: claude-haiku-4-5.

The desktop model picker — two ports, one gateway

Figure 9Two ports, one gateway — how the desktop picker gets readable rows

What

Getting the models to work was configuration; getting them to appear in the Claude Code desktop app was the harder half. The dashboard listed every model and the picker showed only the four claude-* ones.

Two independent causes, neither of them ours: the desktop app ignores ANTHROPIC_BASE_URL and settings.json entirely, reading gateway routing only from its own third-party inference configuration; and its model discovery filters by name, dropping any ID that does not look Anthropic before rendering the picker.

How

  • The rule was read out of the app bundle ([custom-3p] discovery function): a ~50-token vendor deny list is evaluated first as a hard veto, so a claude- prefix cannot rescue an id. Setting inferenceModels explicitly does not help — contrary to the vendor documentation, the same check is applied to an explicit list. On a gateway provider, renaming is not one option among several; it is the only one.
  • Part 1 — the ID must survive the deny list. Each provider model got a second, Claude-shaped, vendor-free alias, each checked against the regex individually: gmn avoids gemini, dsk avoids \bds- and dpsk, zai avoids glm, nvda avoids nemotron.
  • Part 2 — the label. LiteLLM sets display_name to the ID and offers no hook to override it, so picker-shim (nginx on port 4001) rewrites it on the way out via sub_filter. Three details are load-bearing, each learned by breaking it: Accept-Encoding "", proxy_buffering off, and sub_filter_types application/json. Port 4000 and the CLI are unchanged.
  • The trap that costs an hour: GET /v1/models returns the calling key's allowlist, not the gateway's config. Add or rename an alias without running /key/update and the app keeps receiving the old list — which looks exactly like the rename having failed.
  • Setup: Developer Mode → Configure Third-Party Inference; base URL http://localhost:4001 (the shim, not 4000); virtual key as a static bearer token; clear inferenceModels entirely; restart the app, since the picker caches discovery.

Two disclosures. Selecting a free model does not make the session free and does not keep prompts off Anthropic — Claude Code's background traffic (titles, summaries) always goes to a haiku-class model regardless of the picker. And the filter rule lives in the app bundle, so an update can change it without notice: re-verify the picker after every desktop release.
